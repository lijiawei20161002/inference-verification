# 不以成本为主的研究方向

2026-10-20。用户约束：核心创新最好不是低成本。
以下是文献核对后的研究候选，不代表已经实现、已证明新颖或发现现有系统漏洞。
成本保留为部署指标，不作为主要研究命题。当前尚未选定最终路线。

英文实验设计已单独整理：[Explaining and Verifying Numerical Divergence in LLM Inference](../docs/NUMERICAL_CAUSAL_DIAGNOSIS_EXPERIMENTS.md)。
以数值因果定位为主，包含 E0–E5 六组实验；整段执行一致性与可验证边界作为可选扩展。
该文档是实验方案，不是已完成的实验结果。

## 候选一：整段执行一致性

问题：当多种 BF16 执行都合法时，一段输出是否存在一条完整、合法、状态一致的执行路径？

区别在于量词：

- 逐位置的宽松解释：每一步都能找到某个合法配置解释。
- 整段执行解释：能找到一条合法状态演化路径，同时解释所有步骤。

后者必须处理 kernel 切换、KV cache 的历史、prefix 语义、采样随机数计数器。
不能把每个位置各自最有利的参考配置拼接起来，就当成真实可执行的一条轨迹。
这是一种潜在的验证缺口；**尚未证明当前 DiFR 或本仓库存在可利用的这类漏洞**。

最小思想实验：契约规定一次请求只能使用固定的配置 A 或 B。
对同一份候选输出 teacher forcing 后，A 在位置 1 符合、位置 2 不符合；
B 在位置 1 不符合、位置 2 符合。逐位置择优会接受，但不存在符合整段输出的固定配置。
若契约允许 A→B，并且该切换保留合法状态，则这个例子不再构成违规。
因此不能人为禁止生产系统实际允许的转换来制造结果。

算法候选：以带依赖的状态图表达合法转换，用约束传播或路径搜索检查可达性。
有限状态抽象若保留了所有合法行为，则不可达结果可以用于排除；可达仍可能是抽象的伪路径。
对非负局部分数，宽松的逐点最小值与合法路径最小值有：

`sum_t min_c s_t(c) <= min_{path in legal_paths} sum_t s_t(path_t)`。

这个不等式和动态规划都不是创新。难点是设计包含 KV 历史与数值相关性的状态抽象，
避免状态空间膨胀，同时保持合法执行覆盖。经验上枚举少量配置不能直接成为完备证明。

可针对的真实违规包括：契约外的 KV 截断/替换、未声明的 cache 精度转换、
状态不一致的 backend 切换。合法 cache 复用、合法重新计算和合法调度切换必须通过。

最接近工作：

- [IMMACULATE, 2026](https://arxiv.org/abs/2602.22700) 已用混合连续/离散模型、离散状态承诺和可验证计算检查一致性，也分析了自适应行为。泛泛地提出“提交 trace + 验证路径”不新。
- [Bit-Exact Verification, 2026](https://arxiv.org/abs/2606.00279) 已探讨已知执行条件的精确回放。不能把已知完整轨迹的重算称作新问题。

潜在差异：在明确的部分可观测条件下，研究哪些关系约束足以排除“不可能的联合执行”，
并给出可达性保证或最小不一致见证。这需要单独论证，不能宣称严格强于密码学证明。
provider 自报 trace 不可信；token-only 模式可能根本无法识别某些状态违规。

决定性实验：先限制在一个 dense 模型、两种后端、固定采样协议。
对真实合法切换与违反 KV 语义的切换分别采集轨迹。
测试是否存在逐位置/总体分数难以发现，但路径约束能可靠发现的违规。
如果观测不足或普通基线已能同样区分，则该贡献不成立。

## 候选二：数值偏差的因果定位与可复现见证

问题：检测到 BF16 差异后，能否定位实际改变采样结果的执行语义，并给出可复现的反事实证据？

输出不是一个“异常概率”，而是一份诊断：
哪一层、哪个算子、什么输入、何种归约或 cast 差异，如何改变 top-k/top-p 成员，
并最终改变了哪个 token。还需依据事先定义的契约区分合法实现差异与真正违规。

算法候选：

1. 固定 prefix、随机数与操作输入，构建 tensor、kernel 和 KV 状态的依赖图。
2. 从候选集/采样分歧反向切片，寻找可能影响该决定的运算。
3. 对同一算子输入运行参考实现；只替换这一运算及其必要的状态后继，观察分歧是否消失。
4. 做反向注入、阴性对照和交互干预，区分单点原因与多点抵消。
5. 最小化产生现象的输入、shape 和干预集合，输出可独立执行的见证。

技术难点：浮点误差会抵消，多个根因也会交互，失败现象一般不单调。
不能未经验证就用二分搜索把“第一个不同的层”视为根因。
基于删除的最小化通常只能保证集合包含意义下的极小，不能声称全局最小。
单次“替换后恢复”也不证明唯一根因。
有状态算子的干预需要重建依赖的 KV 后继，否则会引入不合法的混合状态。

已有工作限制了可声称的新颖性：

- [Hawkeye, MLSys 2026](https://arxiv.org/abs/2603.20421) 提供 Tensor Core 数值建模和重放。
- [TELLER, 2026](https://arxiv.org/abs/2608.01975) 已做跨层 trace/log 的故障定位；其列出的注入包含资源、延迟、通信与调度扰动。
- [ModelMeta, 2025](https://arxiv.org/abs/2507.04354) 已做模型级变形测试；变形测试概念本身不是贡献。
- [INT8 Conformance, 2026](https://arxiv.org/abs/2609.00363) 已展示某些 epilogue 故障被一 BF16 间隔容差掩盖。

潜在差异：从真实硬件数值语义出发，自动构造“运算差异→候选集变化→token 改变”的因果见证，
并能在新的 GPU/kernel 组合上复现；需要与已有 replay/debugging 方法直接比较。
适用范围应明确为内部诊断或合作式验证，不包装成纯黑盒 API 能力。

主指标：根因定位正确率、反事实修复/反向注入成功率、见证复现率、
合法差异误报率、未见 kernel 的泛化。速度只作工程指标。

当前最自然的起点是归因 49 个 BF16 封顶位置，但归档没有完整 logits/候选集，
需要补采数据。若最终只找到本地 top-p 协议不一致，那是必要修复，不足以支撑此论文。
需要多个真实硬件机制或引擎故障，以及对其他案例有效的统一算法。

## 候选三：可验证性边界与最小观测条件

问题：哪些精度/执行差异能从输出中验证，哪些必须增加共享随机数、中间状态或可信执行证据？

把“质量保持”“输出分布一致”“共享 RNG 下的耦合一致”“执行身份一致”分别定义。
[Statistically-Lossless Quantization, 2026](https://arxiv.org/abs/2605.02404)
明确区分任务指标保持与更严格的分布保真，并用最优耦合下的 token 一致率度量。
这为研究量化后的可辨识性提供了相关对照，但不是 BF16/INT8 不可区分的现成证明。

一个标准起点：令 P 是某个合法实现、Q 是待检实现的完整可观测审计 transcript 分布。
若在 P 上误报不超过 alpha，则任意拒绝事件在 Q 上的概率至多
`alpha + TV(P,Q)`（上限为 1）。这个基本界本身不构成创新。

研究贡献需要是特定系统条件下的紧界、可达到该界的检验或必要观测，
以及真实 BF16/量化实现的匹配构造。不能从当前 INT8 5/64 的低检出率推导任何不可能性。
高维输出上的经验小距离也不等于已证明 TV 上界。

共享 seed 会改变观测：应比较 `(seed, output)` 的联合分布，不能套用无 seed 的边缘分布距离。
有限长度和自适应查询还要求分析整个交互过程，而非单步、固定 prompt 的分布。
若某种新增信息能打破原来的不可辨识，必须说明其可信来源与部署条件；
签名的自报日志并不自动证明实际执行。

最接近的 [Are You Getting What You Pay For?, 2025](https://arxiv.org/abs/2504.04715)
已讨论输出与 log-prob 审计的限制及 TEE 方案；仅重复“黑盒方法可能失败”不新。
需要给出更细的边界：在什么硬件变化、采样约定、输入家族和观测条件下能保证什么。

主指标：保证是否成立、界是否紧、所需观测是否必要、跨条件是否可迁移。
这条路线理论负担较高；经验上失败的图表不足以支撑。

## 建议排序

| 方向 | 首要贡献 | 当前可执行性 | 最大风险 |
|---|---|---|---|
| 数值因果定位 | 可复现、可干预的故障解释 | 最适合从现有 BF16 问题起步 | 只得到几个手工案例，缺少通用方法 |
| 整段执行一致性 | 更强的执行语义与联合约束 | 概念更有野心，先做小范围原型 | 可观测性不足；与已有承诺/回放方案重叠 |
| 可验证性边界 | 明确哪些保证可实现及需要什么信息 | 可复用量化与跨 GPU 实验 | 只能证明抽象结论，无法连接真实系统 |

面向当前项目，我建议先验证数值因果定位是否能产生跨案例的统一方法，
将整段执行一致性保留为更有野心的候选，暂不把三条合并成一篇论文。
论文的主要图应展示解释/保证/覆盖能力；性能和成本放在部署评估。
