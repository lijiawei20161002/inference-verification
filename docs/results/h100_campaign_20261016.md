# H100 campaign results — 16 October 2026

[Documentation](../README.md) · [Experiment guide](../MULTI_MACHINE_EXPERIMENTS.md) ·
[Archived measurements](h100_campaign_20261016/) ·
[Recomputed summary](h100_campaign_20261016/summary.json)

**All eight scheduled baseline tasks completed by 06:19:35 UTC.** This campaign
supports context-length timing as a useful local signal and shows why both
timing and token-score calibration must match the execution setup. It does not
establish deployment false-positive rates, cross-hardware transfer, or an
improvement from combining the two channels.

The strongest positive result is the controlled interference pilot: all four
shortened-context conditions raised alarms in all 16 test cycles, both with
and without a workload on the second GPU. The full-context control raised
0/16 alarms in each condition. The most important limitation is that the timing
curve changes substantially between the tested serving paths; a threshold
calibrated on one path cannot be presumed valid on another.

## 1. Honest replay changes move token scores

Sources: [1.7B](h100_campaign_20261016/token-1.7B.json),
[4B](h100_campaign_20261016/token-4B.json).

Each model generated one honest pool of 80 sequences × 256 positions, then
replayed those same tokens under different verifier schedules. BF16 weights,
temperature 1, top-k 50, top-p 0.95, and sampling seed 42 were used. The prompts
come from the first 80 entries of `HFGPUBackend.DEFAULT_PROMPTS`, truncated to
32 prompt tokens. Only the **clean** arm ran: injected verifier logit and
activation noise were disabled. No attack was generated in these jobs.

The table reports `token_difr` d′, the change in mean score divided by the
baseline score standard deviation. Scores are winsorized using the baseline
99.9th percentile. Intervals are **90% paired sequence-bootstrap intervals**
from 400 resamples, not 95% intervals or per-token independent error bars.

| Model | Verifier change from batch-1 eager prefill | d′ | 90% interval |
|---|---|---:|---|
| Qwen3-1.7B | Batch 4, with 3 unrelated filler rows | 0.00000 | [0, 0] |
| Qwen3-1.7B | SDPA attention | +0.01184 | [−0.00002, +0.02332] |
| Qwen3-1.7B | Sequential KV-cache replay | −0.02813 | [−0.03751, −0.01821] |
| Qwen3-4B | Batch 4, with 3 unrelated filler rows | 0.00000 | [0, 0] |
| Qwen3-4B | SDPA attention | +0.00134 | [−0.00807, +0.01187] |
| Qwen3-4B | Sequential KV-cache replay | −0.03109 | [−0.04098, −0.02200] |

The same-shape rerun control and batch-4 comparison had identical scores for
all four detectors in both models. SDPA's `token_difr` intervals include zero;
sequential replay produces a small, consistently negative shift. A negative
shift moves away from this detector's high-score alarm direction, but it is
still a change in the honest distribution.

The activation detector is much more schedule-sensitive: sequential replay
changes `activation_difr` by −1.61797 d′ for 1.7B and −1.78614 for 4B.
Activation scores require internal evidence and are an additional-visibility
control, not part of a public-token-only check. The archived
`frac_tokens_changed` field counts **changed scores at token positions**; it
does not mean that generated tokens changed, since each comparison reuses the
same returned tokens.

**Implication:** batching these particular audits was benign, while changing
attention or replay paths requires calibration checks. There is no measured
attack power, AUC, or deployment FPR here. The raw files also contain legacy
`price_of_the_floor` calculations using historical 1.7B attack effect sizes.
Those are not new measurements: they mix earlier noisy/simulated-attack
references with this clean arm, and reuse 1.7B references for the 4B run.
They must not be presented as validated detection costs or cross-model results.
The two model jobs ran independently on different H100s; neither replayed the
other GPU's capture.

## 2. Effective context length has a strong local timing signal

Source: [clock-window.json](h100_campaign_20261016/clock-window.json).
Qwen3-1.7B BF16, batch 1, CUDA graph with static KV cache, 192 decode steps ×
4 repetitions per setting. Timings use the **host clock plus CUDA
synchronization**. They include measurement overhead and are not client
network arrival times or pure kernel times.

| Effective context | Mean decode interval, ms | Difference from 256-token context, ms |
|---:|---:|---:|
| 256 | 5.531 | 0.000 |
| 512 | 5.893 | 0.362 |
| 2,048 | 7.962 | 2.431 |
| 8,192 | 16.786 | 11.254 |
| 16,384 | 28.395 | 22.864 |
| 32,768 | 50.732 | 45.201 |

The immediately subsequent [stability run](h100_campaign_20261016/clock-stability.json)
gave a full-minus-short gap of 45.179 ms. Mean timings differed by at most
0.023 ms at shared context settings. This is short-term repeatability over
minutes, not a test across days, hosts, or software updates.

These experiments vary the actual input/cache length using a repeated text
fixture. They do not submit one identical long request through a network
provider that secretly truncates it. The result supports the mechanism behind
a context probe; a real truncation detector still needs that end-to-end test,
along with controls for caching, buffering, and workload.

## 3. A second-GPU workload did not defeat this pilot

Source: [clock-interference.json](h100_campaign_20261016/clock-interference.json).
GPU 0 measured Qwen3-1.7B while GPU 1 either paused or ran 8192 × 8192 BF16
matrix multiplications, 16 operations per synchronized loop. Recorded counters
confirm work occurred in every load cycle and none in idle cycles.

Sixteen idle calibration cycles set a threshold of **45.144632 ms** for the
long-minus-256-token timing difference. The alarm rule is strictly below that
threshold. Test data comprise 16 idle/load pairs, with counterbalanced condition
order and randomized context order shared within each pair. Each cycle measures
six contexts and 192 decode intervals per context. The observation unit for
alarm rates is the cycle, not the individual interval.

| Effective context | Idle gap, ms | Load gap, ms | Idle alarms | Load alarms |
|---:|---:|---:|---:|---:|
| 512 | 0.382 | 0.381 | 16/16 | 16/16 |
| 2,048 | 2.421 | 2.419 | 16/16 | 16/16 |
| 8,192 | 11.277 | 11.277 | 16/16 | 16/16 |
| 16,384 | 22.831 | 22.862 | 16/16 | 16/16 |
| 32,768, honest control | 45.432 | 45.345 | 0/16 | 0/16 |

**Implication:** the tested shortened contexts remain clearly separated from
the full-context control under this particular second-GPU load. The finding
does not cover same-GPU contention, network queues, CPU saturation, or deliberate
context-dependent padding.

The configured `target_fpr=0.005` is a target, not an achieved guarantee. With
only 16 calibration cycles, the script's lower empirical quantile is simply
the smallest observed calibration gap. Even assuming independent identical
Bernoulli trials, 0/16 errors has a one-sided 95% upper bound of **17.1%**;
16/16 detections has a corresponding lower bound of **82.9%**. These are
illustrative per-condition bounds, not simultaneous bounds or deployment
intervals: repeated text and shared machine conditions limit generalization.
Neither pooling token intervals nor merging the paired idle/load observations
creates the independent evidence needed for a 0.5% FPR claim.

## 4. Timing depends strongly on stack, batching, and quantization

Sources: [floor](h100_campaign_20261016/clock-floor.json),
[batching retry](h100_campaign_20261016/clock-batching.json).
The floor grid contains four model/precision configurations × two execution
paths × six contexts. Each cell uses 192 steps × 4 repetitions at batch 1.

| Model/weights | Execution path | 256-token interval, ms | 32,768-token interval, ms | Difference, ms |
|---|---|---:|---:|---:|
| Qwen3-0.6B BF16 | CUDA graph | 4.700 | 50.640 | 45.940 |
| Qwen3-0.6B BF16 | HF eager loop | 15.288 | 15.473 | 0.185 |
| Qwen3-1.7B BF16 | CUDA graph | 5.540 | 50.745 | 45.206 |
| Qwen3-1.7B BF16 | HF eager loop | 16.525 | 15.632 | −0.893 |
| Qwen3-4B BF16 | CUDA graph | 8.643 | 76.504 | 67.861 |
| Qwen3-4B BF16 | HF eager loop | 20.032 | 20.459 | 0.426 |
| Qwen3-1.7B actual NF4 | CUDA graph | 5.207 | 50.982 | 45.775 |
| Qwen3-1.7B actual NF4 | HF eager loop | 20.841 | 20.717 | −0.125 |

The graph path uses a static cache; the eager loop uses a dynamic cache, and
the clock script does not explicitly fix the attention implementation at model
load. These are compound execution-path comparisons. The near-flat eager
curve does not prove that context was dropped, and the measurements do not
isolate which kernel/cache/overhead difference caused it. No production vLLM
stack was tested. In particular, the 45.14 ms graph threshold above must not
be transferred to the eager path unchanged.

Batch size also changes the honest timing baseline. Selected Qwen3-1.7B BF16
cells from the complete 84-cell retry:

| Context | Batch | CUDA graph interval, ms | HF eager interval, ms |
|---:|---:|---:|---:|
| 1,024 | 1 | 6.547 | 15.894 |
| 1,024 | 64 | 35.173 | 20.850 |
| 8,192 | 1 | 16.582 | 15.783 |
| 8,192 | 64 | 191.965 | 101.212 |

These are batch-step intervals: each step advances all B sequences. They are
not batch throughput expressed as milliseconds per aggregate emitted token.

Actual NF4 is not a reliable fast-provider signature. In the floor run its
short-context graph interval was slightly smaller than BF16's, but its
long-context interval was slightly larger; the eager NF4 path was slower at
both endpoints. In the batching retry at context 1,024 and batch 4, NF4 took
9.496 ms versus BF16's 8.115 ms in graph mode. This measures execution time
with real quantized weights, not the ability of token scores to detect them.

**Implication:** use timing evidence conditioned on a calibrated execution
regime. These results do not support inferring model identity or quantization
from a universal absolute-speed threshold. A context signal can be strong in
one regime and weak in another.

## 5. Speculative decoding creates bursts without establishing misconduct

Source: [clock-specdec.json](h100_campaign_20261016/clock-specdec.json).
Qwen3-0.6B drafts four tokens for a Qwen3-1.7B target at initial context 512.
The implementation uses greedy acceptance, 64 blocks × 3 repetitions; these
counts are fixed by the legacy function rather than the general timing flags.

The 192 blocks emitted 604 tokens, or **3.146 tokens/block**. Mean block time
was 87.777 ms and amortized time was 27.903 ms/token. Assigning the block's time
to its first emitted token and zero to the rest produces **68.2% zero gaps**.
Those zero gaps are constructed from measured device-side blocks; they were
not observed on a network connection. This run also does not validate exact
token equality against a separate sequential decoding run.

**Implication:** an individual zero or very short arrival gap is insufficient
evidence of cheating. A network verifier needs event boundaries, emitted token
counts, and block/window-level analysis. This experiment motivates that design
but does not measure the behavior of a real streaming endpoint.

## What this changes and what should run next

The campaign provides a completed local baseline, an encouraging controlled-load
result for context timing, and direct evidence that execution conditions affect
both channels. It gives a reason to test joint verification, but no joint
advantage has yet been measured: these jobs did not score token and timing
evidence from the same requests against an independently calibrated combined
decision rule.

The next measurements should resolve these specific gaps:

1. **Serving-path correctness and transfer.** Verify full-context cache usage
   and output consistency in the eager and graph paths, then repeat probes on
   a pinned production serving stack. Establish a separate honest baseline per
   allowed regime before testing transfer.
2. **Fresh held-out requests and time periods.** Repeat across days, prompts,
   batching/load conditions, and hardware. Use request/session-level uncertainty
   and enough independent calibration/test blocks to assess the chosen FPR.
3. **Same-request joint evidence.** Capture returned tokens and client-side
   streaming events together; compare token-only, timing-only, and joint
   decisions at the same overall false-positive budget.
4. **Actual deviations and adaptive behavior.** Test real NF4/INT8 token
   detection, actual truncation of identical long requests, model substitution,
   buffering, and deliberate padding. The current timing pilot did not test
   those adversaries end to end.

## Reproducibility

[provenance.json](h100_campaign_20261016/provenance.json) records every result's
hash, original run directory name, code revision, parameters, runtime, model
revision, and selected package versions, including the superseded attempt.
The archived JSON files are byte-for-byte copies of the original results;
historical results elsewhere in `docs/results/` are unchanged.

Hardware was one host with two NVIDIA H100 80GB HBM3 GPUs. Software was Python
3.12.3, PyTorch 2.8.0+cu128, Transformers 4.57.6, bitsandbytes 0.50.2,
NumPy 2.1.2, and driver 580.126.09. PyTorch's runtime is CUDA 12.8; the driver's
reported CUDA capability is 13.0. BF16 is the base precision; the NF4 load uses
bitsandbytes double quantization and BF16 computation.

|---|---|
| Qwen/Qwen3-0.6B | `c1899de289a04d12100db370d81485cdf75e47ca` |

Rebuild or verify the numerical summary without a GPU or third-party packages:

```sh
python3 experiments/analyze_h100_campaign.py
python3 experiments/analyze_h100_campaign.py --check
```

The analysis checks all nine artifact hashes, the final task set, the complete
floor and batching grids, rerun controls, and interference cycle coverage. It
recomputes the threshold, alarm counts, and mean differences from the recorded
interval arrays, and verifies the speculative gap arithmetic. It cannot recover
unarchived per-sequence token scores, so the original bootstrap intervals are
preserved rather than independently re-estimated.

For fresh GPU runs, follow the [environment/model-lock setup](../MULTI_MACHINE_EXPERIMENTS.md)
in a clean checkout at the appropriate revision above. Set `HF_HUB_OFFLINE=1`
and `TRANSFORMERS_OFFLINE=1` after populating the pinned cache. Use the same
model-lock JSON (the `models` mapping in provenance), with its path supplied as
`MODEL_LOCK`. At `cc8994a...` the seven successful task commands are:

```sh
python scripts/run_research_job.py --node h100-sxm-01 --gpu 0 --job token-shape --size baseline --model Qwen/Qwen3-1.7B --model-lock "$MODEL_LOCK"
python scripts/run_research_job.py --node h100-sxm-01 --gpu 1 --job token-shape --size baseline --model Qwen/Qwen3-4B --model-lock "$MODEL_LOCK"
for job in clock-window clock-stability clock-floor clock-specdec; do
  python scripts/run_research_job.py --node h100-sxm-01 --gpu 0 --job "$job" --size baseline --model-lock "$MODEL_LOCK" || break
done
python scripts/run_research_job.py --node h100-sxm-01 --gpu 0 --load-gpu 1 --job clock-interference --size baseline --model-lock "$MODEL_LOCK"
```

At `b8bfacb...`, reproduce the completed batching grid with:

```sh
python scripts/run_research_job.py --node h100-sxm-01 --gpu 0 --job clock-batching --size baseline --model-lock "$MODEL_LOCK"
```

Only the two token jobs may overlap. Timing baselines require an otherwise idle
host; the interference job supplies its own controlled second-GPU workload.
Fresh timings need not be bit-identical to this campaign.
