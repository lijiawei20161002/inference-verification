# Inference Verification：基于硬件机制的性能探针实验设计

Version: v0.2 · 2026-10-19 · Status: first L40S mechanism pilot completed.

[English results and reproducible evidence](results/performance_probes_l40s_20261019.md):
524 local measurements covering P0/P1/P4, 42 loopback HTTP requests, and 96
equivalent-SDPA controls. The pilot does not complete production calibration,
precision probes, capacity frontiers, or adaptive evasion. Proposed thresholds
and acceptance criteria below remain design targets.

目标是检验：能否利用推理过程中的访存、计算、缓存、流水线和调度机制，构造一组主动性能探针，在明确的服务条件下区分符合声明的执行与上下文截断、未声明的精度降级等偏差。

本文优先追求“硬件机制 → 可干预变量 → 可观测响应 → 可证伪判据”的证据链。性能差异本身不构成违规证据；正确的内核优化、合法缓存和调度变化必须进入正常对照。所有新增阈值、样本量和验收目标均为设计建议，不是已有实测结果。

**1. 研究问题与适用范围。** 首轮研究对象是已知权重和 tokenizer 的稠密 decoder-only 模型、单 GPU 服务。首先研究全上下文 BF16 声明，分别施加上下文窗口缩短、真实 NF4/INT8 权重量化、可支持的真实 KV cache 量化。只有违反该轮明确声明的改动才标为偏差；模型原生 sliding-window、服务商已声明的量化、合法前缀缓存均不能自动标为违规。

我们要回答三个问题：

1. 在固定硬件和服务栈下，偏差是否改变预先预测的响应曲线？
2. 这种变化是否能与正常的批处理、kernel、缓存和负载变化区分？
3. 去掉本地计数器和调度日志后，客户端可见的信号还剩多少？

最终输出分为“与已覆盖正常条件不一致”“未发现偏差”和“条件不适用，无法判断”。不能从单个延迟数值认证 GPU 型号、权重位宽或完整模型执行。未知的多 GPU 路由、MoE 路由、卸载和 prefill/decode 分离会引入新的假设，首轮不混入单 GPU 结论。

**2. 现有证据决定了哪些假设必须重新检验。** 仓库的 clock 实验已经发现：真实量化的时间收益并不随权重字节数同比变化；某些批量下 NF4 反而更慢；合法推测解码和传输合并可以产生很短的客户端事件间隔。这些结果支持继续研究响应曲线，但不支持普适的“速度越快越可疑”规则。[仓库测量记录，固定提交 94fedda](https://github.com/lijiawei20161002/inference-verification/blob/94fedda46dd0d2cc2546a571e2a7df3406cfae96/docs/CLOCK_MEASURED.md)

特别需要检验已有文档中“负载只会抬高上下文斜率”的推断：调度切换、缓存、分块 prefill、动态 batching 可能改变差分两端的执行条件；先前栅格中的观察不能作为跨服务栈的单调性定理。

本设计保留差分方法，但只声称：固定的加性开销可由差分抵消。随上下文、并发或路由变化的开销不会自动抵消。首轮源码也需修正并固定 top-p 语义；旧采样器产生的测量单独保留，不直接继承其阈值。

**3. 观测权限决定结论强度。**

| 层级 | 我们可控制或读取的内容 | 主要用途 |
|---|---|---|
| A：本地机制实验 | 实际 batch、kernel、KV 格式、GPU 时间线、显存与计数器 | 验证因果解释，建立正常和偏差对照 |
| B：自有 HTTP 服务 | 客户端请求与流式事件；服务器日志仅用于事后对照 | 测试哪些信号能穿过调度和网络 |
| C：远端黑盒 API | 文本、请求时间、并发与返回事件；通常无可信 batch/计数器 | 在匹配的校准范围内做行为检验 |

A 层观察到的硬件指标不得作为 B/C 层检测器的隐藏输入。服务器自行返回的执行时间、位宽和 batch 标签不视为独立可信证据。公共 API 的并发只在约定配额内测试；容量饱和与干扰实验限定在自有或明确授权的部署上。

**4. 共同的硬件假设与计时定义。** 对单个 dense decode step，权重读取、KV 访问、矩阵计算和调度共同影响延迟。以未压缩、未共享、未卸载的标准 KV 存储为参考，其逻辑字节数为：

`M_KV ≈ 2 × N_layers × N_KV_heads × head_dim × bytes_per_element × Σ_i L_i`

这里 2 对应 K/V，L_i 是第 i 个活跃序列的已存储长度。分页、对齐、量化元数据、共享前缀和缓存预算会改变实际占用；逻辑字节数也不等于每一步实际 HBM 流量。

计算量/有效吞吐、流量/有效带宽可形成资源下界和瓶颈预测，但不能直接相加作为总时间；异步拷贝与计算会重叠，解量化与同步又可能增加关键路径。Hopper 的 TMA 支持异步数据搬运，attention 优化也会通过计算与搬运重叠改变性能。[Hopper 架构文档](https://docs.nvidia.com/cuda/hopper-tuning-guide/index.html)、[FlashAttention-3](https://arxiv.org/abs/2407.08608)

统一记录四类时间：

- **TTFT**：客户端完成发送请求至收到第一个非空生成内容；包括排队、prefill、传输，不能直接当作 GPU prefill 时间。
- **生成阶段整体速率**：整段输出数量与首尾内容事件的时间跨度，明确输出计数来源。
- **事件间隔与每事件内容量**：保留原始流式事件。没有准确 token 边界时，不把 SSE chunk 当成一个 token，也不报告精确逐 token ITL。
- **本地分解**：排队、prefill、decode step 和网络发送时间。跨主机不直接相减未同步的时钟；单端使用单调时钟，靠请求 ID 对齐。

将客户端并发 C 与 GPU 实际 batch B 分开记录。C 是客户端可以施加的变量，B 是服务端调度结果。固定 batch 的单步延迟、单请求生成速率与总吞吐分别报告。

**5. 机器与统一控制。** 主机建议为单张独占 H100 80GB，16 核 CPU、128GB RAM、200GB 可用 SSD；CPU/内存/磁盘为工程配置建议，不是最低要求。已有 L40S 可先跑低成本试验；机制成立后用 A100 或 L40S 做迁移检验。首轮不需要 B200 或多 GPU。

以 Qwen3-1.7B 的已归档权重版本为起点；固定模型、tokenizer、代码提交、CUDA、驱动、推理引擎、量化参数与编译产物。对照硬件时固定可固定的软件项，记录无法匹配的项。以现有 HF 路径连接历史结果，再选一个固定版本的生产推理引擎验证迁移；不同引擎作为独立条件。

执行要求：

- 记录 GPU SKU、时钟、功耗限制、温度、显存预算及其他进程；基础实验关闭共享干扰，负载变化另设对照。
- 确认 Nsight Compute 计数器可用。计数器仅在少量代表点采集，主计时使用不挂 profiler 的独立运行。[计数器权限](https://developer.nvidia.com/nvidia-development-tools-solutions-err-nvgpuctrperm-nsightcompute)
- Nsight Compute 的 replay、缓存清理与时钟控制可能改变执行条件，profile 结果不能直接替代自然执行延迟。[Profiling Guide](https://docs.nvidia.com/nsight-compute/ProfilingGuide/index.html)
- 不在每个 decode token 内进行用于诊断的 CPU 拷贝、同步或激活导出。诊断另跑一次，避免测到采集开销。
- 分清 JIT/图捕获预热、模型驻留、硬件缓存热度与前缀 KV 缓存；分别记录，不用统一的“warm”标签。
- 每个配对组随机化 AB/BA 顺序；形状改变时记录实际 kernel 与 padding/graph bucket，不能只记录请求参数。
- 固定前缀/续写重放用于机制归因；独立自由生成用于端到端验证。重放的时间结果不直接当作真实服务分布。

**6. 实验 P0：测量链路校验。** 优先级：必须先做。机器：现有 GPU 即可。

先在同一个自有服务中同时采集客户端事件、服务端阶段日志和少量 GPU 时间线。比较无 profiler、挂时间线工具、挂计数器工具三种测量条件。使用同一模型和输出预算，显式控制是否缓冲流式输出。

**最小设计：** 选择短/长两个上下文与低/高两个批量，完成 4 个代表点；每点 20 次技术重复，分散在至少 3 次进程启动中。技术重复用于评估计时噪声，不作为 60 个独立部署样本。

**交付：** 一张分阶段时间图、一次事件合并的原始轨迹、测量工具开销表，以及 C 与实际 B 的对应记录。

**停止条件：** 如果客户端差异主要来自 tokenization、CPU 采样、同步诊断或输出缓冲，先修测量路径；不进入位宽或上下文的物理解释。

**7. 实验 P1：上下文长度 × 批量的响应面。** 优先级：第一组正式机制实验。目标偏差：未声明的上下文截断。

**机制预测：** 在其他条件固定且 attention 正常访问完整历史时，增长 L 会增加相关工作；固定窗口 W 的实现可能在 L 超过 W 后出现增长放缓。批量改变可能影响带宽利用、occupancy 和调度，因此检验 L 与 B 的交互，而不预设全局线性或单调下界。

**本地栅格：** L ∈ {512, 2048, 8192, 16384}，固定实际 B ∈ {1, 4, 8}，每条输出预算 128 token。比较全上下文 BF16 与明确截断到 W=2048 的实现。L≤W 是内置负对照。按 12 个形状、2 个执行条件、8 个独立文本/运行块开展探索，共 192 个批次单元；每批次包含 B 条序列。显存预检不通过的格点明确标为不可运行。

**截断实现：** “prefill 前删除早期输入”和“完整 prefill 后、decode 时驱逐早期 KV”分成不同条件，不能混为一个攻击标签；记录 position IDs、RoPE 位置策略与实际参与 attention 的位置。第一轮先选其中一个明确实现，另一个作为后续泛化测试。

**观测：** TTFT、生成阶段速率、固定位置区间的 decode step 时间、上下文有限差分斜率、L 与 B 的交互、实际 KV 访问和 attention kernel。L 是起始长度；若输出期间增长不可忽略，按相同输出位置分层。

**正常对照：** CUDA Graph、不同正确 attention kernel、chunked prefill、动态 batch 和适量受控后台负载。先逐项变化，再组合最容易混淆的条件。chunked prefill 会把 prefill 与 decode 工作交错，是必须覆盖的调度因素。[vLLM 调度说明](https://docs.vllm.ai/en/v0.22.0/configuration/optimization/)

**可支持的结论：** 在所覆盖条件下，响应面是否能区分完整上下文与该种截断。

**证伪条件：** 正常 kernel/调度变化同样产生无法区分的斜率折点；或者本地明显的信号经 HTTP 后消失。出现这些情况时缩小适用条件或报告不可分辨，不能把折点直接解释为截断。

**8. 实验 P2：量化后的访存节省与解量化代价。** 优先级：第二组。目标偏差：未声明的权重或 KV 精度变化。

**机制预测：** 权重量化同时改变权重流量、解包/解量化、矩阵执行路径和资源使用。改变 B 与 L 可重新分配这些成本，所以有价值的信号是相对响应随负载的变化；量化更快或更慢都可能成立。已有量化系统工作也将运行时解量化开销列为核心问题。[Quant-LLM](https://www.usenix.org/conference/atc24/presentation/xia)

**最小设计：** 权重 BF16/NF4/INT8 × L ∈ {512,8192} × B ∈ {1,4,8}，共 18 个条件；先用独立冻结输入重放，再在筛选出的条件做自由生成。先固定 BF16 KV；权重实验完成后，才单独切换实际支持的 KV 格式，避免同时改变两类精度。

**必须核实：** packed 权重、计算 dtype、累加路径、实际调用 kernel、CPU offload 与隐式转换。若某引擎不支持匹配的量化实现，该格点标为不支持，不以模拟 logit 噪声或 CPU 卸载替代。

**主要特征：** 各 L 下的 batch 响应比、各 B 下的上下文响应比、TTFT 与生成阶段时间的联合变化；比值同时保留原始分母和置信区间。机制诊断另记录权重/attention 时间占比、DRAM 字节、L2 行为、Tensor Core 与相关指令活动。

**关键对照：** 同为 BF16 的不同正确 kernel 和频率条件；同一种量化的不同实现。性能探针若只识别出一个库或低效 kernel，结论限定为实现指纹。

**证伪条件：** 同位宽不同实现的差异覆盖了跨位宽差异，或正常频率/调度变化能复现相同响应。此时不能声称位宽识别；保留它作为有条件的异常检测或负结果。

**9. 实验 P3：内核切换、分块边界与资源台阶。** 优先级：探索性；P1/P2 有稳定信号后再做。

**机制预测：** tile 数量、padding、graph bucket、shared memory 和寄存器需求会影响 occupancy 或触发 kernel 切换。若偏差改变了执行路径，响应曲线的局部台阶可能变化。这个假设首先是实现级的，尚不是 GPU 或精度的唯一指纹。

**设计：** 从本地 trace 确认一个实际 tile、graph 或 dispatch 边界，再测其两侧，例如 b−2、b−1、b、b+1、b+2；同时在远离边界的区域设置相同密度对照。B 可从 {1,2,3,4,7,8,9} 起步；L 的密集扫描点由已观察的边界确定，不预设“某个整数必然对应某种硬件”。

**观测：** 局部延迟跳变、曲率、kernel ID、实际 padding 后形状、资源使用及边界是否随执行模式移动。控制模型与语义输入，避免把不同模板或路由的变化混入形状效应。

**对照与证伪：** 固定 kernel 后台阶消失、关闭 graph bucketing 后台阶移动，都能帮助归因。若软件版本升级或正常 batching 就使台阶漂移，且无法在独立部署复现，则放弃把它用于通用验证。实验发现的边界只用于后续新数据，不能在同一曲线上选边界再报告显著性。

**10. 实验 P4：区分合法前缀缓存与少算上下文。** 优先级：P1 的必要对照。

**机制预测：** 正确的 prefix KV reuse 可减少重复前缀的 prefill，但后续 decode 仍应使用相应的历史 KV。其直接收益主要落在 prefill；实际端到端调度可能带来间接变化，所以不要求 decode 时间严格不变。[vLLM Prefix Caching](https://docs.vllm.ai/en/v0.13.0/features/automatic_prefix_caching/)

**设计：** 使用多个互不相同的长前缀，每个前缀分配多个短后缀；比较 cache 明确关闭、开启且命中、开启但冷未命中三组，再加入上下文截断组。本地明确清缓存或使用有效的隔离机制，同时保持 JIT 和模型预热一致。不要用“换了后缀”作为整个前缀缓存失效的依据。

**观测：** TTFT 的冷暖差、decode 对总历史长度的响应、实际 cached-token 数和 KV 访问。冷暖状态仅用于本地解释，远端不依赖服务商自报的 cache 标签。

**预期判别：** 联合使用“prefill 是否节省”和“decode 是否仍随历史变化”，检验其是否比单看 TTFT 更能排除合法缓存造成的误报。

**证伪条件：** 调度、KV 布局或路由变化使两类响应在客户端不可区分；此时应将缓存状态列为未识别因素，不能指控少算。文本内容正确性可作辅助对照，但通过内容检查不能证明完整计算。

**11. 实验 P5：显存容量与服务容量前沿。** 优先级：本地第二阶段。目标：探索位宽影响容量、但不明显影响单请求速度的情况。

**机制预测：** 给定明确的模型驻留、KV 格式、单 GPU 显存预算和无共享/卸载条件，增加总活跃 token 数会增加 KV 压力。减少权重或 KV 占用可能移动可服务区域，但算力、调度和 admission policy 也可能先成为限制。

**设计：** 在固定显存预算下逐步提高活跃序列数与 L。分别记录最大驻留范围、排队出现点、调度 preemption、KV eviction/recompute/offload，以及达到预先指定延迟目标时的吞吐。容量前沿同时报告内存限制与延迟限制，不合并成一个数字。先在自有服务中预估占用并设置停止线，不以反复 OOM 为测试方法。

**对照：** 固定并记录 KV pool 预分配预算、关闭 prefix sharing；再单独开启共享/卸载检验混淆。实验性调低显存预算可以加快定位边界，但所得边界属于该预算，不能冒充整卡容量。

**可支持的结论：** 已知配置下，资源使用是否与声明相符。

**证伪条件：** 相同前沿可由合理的 admission policy、KV 预算或正常 offload 产生；未知远端硬件数量也会破坏解释。仅靠“能同时接更多请求”无法认证量化或 GPU 数量。

**12. 实验 P6：缓冲、延迟填充与自适应规避。** 优先级：进入远端验证前必须完成。

**机制预测：** 网络分块可以改变逐事件间隔；恒定延迟只影响某些绝对量，而按请求特征调整的延迟可能改变差分和整条曲线。更便宜的执行若有足够时间余量，可以通过等待模仿某些正常轨迹。多维探针是否提高伪装代价需要实测。

**自有代理设计：** 在正常与偏差服务前加可控代理，分别测试固定排队延迟、随机抖动、每 k 个 token 合并发送、带定时器的缓冲、按 L/C 条件化的延迟，以及自适应拟合正常时间曲线。流式发送应遵守 token 已产生的因果约束；若完整缓冲才能匹配，计入其 TTFT 和用户体验代价。

**观测：** 检出率—额外延迟—吞吐损失的规避曲线，以及通过伪装后保留的显存/资源收益。额外等待不一定增加同等 GPU 计算成本，分别记录 GPU 活跃时间、占用容量与客户端等待。

**正常对照：** 对符合声明的服务施加同样的网络/缓冲处理，检查误报；在支持且有正确性对照的部署中加入合法推测解码。

**证伪条件：** 偏差服务可以以小代价同时匹配所有客户端可见特征。此时应明确报告纯性能通道的识别边界。若允许服务商任意按审计请求选择执行路径，本文不主张不可规避的硬件证明。

**13. 从实验结果形成检测算法。** 在开发数据上选择少量机制明确的成对探针，固定请求集合、顺序随机化规则、输出预算和统计特征。一个候选特征向量可以包括：TTFT 长短差、生成速率的上下文响应、并发交互、冷暖响应差和预注册的局部边界变化。只纳入该访问层实际可获取的特征。

先使用简单的正常条件距离/残差评分，并保留各特征贡献。比较四个同预算基线：绝对延迟、单一上下文斜率、无机制约束的统计分类器、机制驱动的组合探针。这样才能区分收益究竟来自硬件推导，还是仅来自增加请求数量。

**统计单位是一整次 audit block。** 一个 block 包含完整探针组合；同一序列的 token、同一批次内请求和同一运行会话不能假定独立。按独立时间块/会话做聚类分析，不把 profiler 的重复 replay 当成新增样本。

开发、校准和最终评估分离。开发阶段选特征与超参数；校准只用新采集的正常 block；最终评估使用新的文本与运行会话。迁移到未覆盖的硬件/服务条件时先报告迁移结果，不默认沿用原有保证。

对多个已覆盖正常条件，可预先为每个条件校准同一套冻结评分流程，并以“至少一个正常条件能解释”为接受规则。例如对各正常条件得到有效的 p 值 p_j 后，使用 max_j p_j 检验这些正常条件的并集。该做法可能牺牲功效，且不覆盖未表示的条件；不能对所有条件取最小 p 值后仍声称维持原误报率。[Conformal 校准与组合检验背景](https://arxiv.org/html/2107.07511v6)

每个 block 输出一次主要判决。分别检验多个探针、多个预算或反复查看中间结果，需要联合校准或预先分配错误预算。自适应选点用于探索；最终确认使用冻结策略和新数据。

**14. 分阶段样本量、成本与验收。** 第一阶段的 8 个探索 block 用于排查机制和采集故障，不足以建立低误报结论。只有通过机制检验的少量探针才进入独立校准。

一个可执行的确认阶段起点是：每个主要正常条件 199 个新校准 block、400 个独立正常评估 block；每种关键偏差另采集 200 个评估 block。若时间相关性明显，以独立会话为单位增加采集，不能依靠增加同会话 token 数补足样本。

建议将单次 audit 的校准目标先设为 2.5%，留出有限样本验收余量；这是设计选择，不是自动的部署保证。候选成功标准为：在预先列明的正常条件内，误报率的单侧 95% 上界不超过 5%；关键偏差检出率的单侧 95% 下界至少达到 80%。逐条件报告，并说明跨条件/多比较是否进行了同时覆盖校正。未达标时报告结果，不能在测试集上反复改阈值直到通过。

所有比较固定总预算：请求数、输入/输出 token、GPU 时间、客户端等待和费用（若有）。P1 栅格的 192 个“批次单元”不等于 192 个 API 请求；请求数还要乘以各批次 B。

先测代表格点的无 profiler 耗时，再估算完整运行：

`GPU 时间预算 ≈ Σ(格点 × 独立 block × 单元实测耗时) + 模型加载/编译 + 单独 profiling`

不得把历史单次 pilot 的用时直接当作新栅格总预算。费用上限和运行停止条件在真实执行前写入配置；本文仅制定实验，不触发租机、付费 API 调用或压力测试。

**15. 推荐执行顺序与可交付结果。**

| 阶段 | 执行内容 | 进入下一阶段的条件 |
|---|---|---|
| A | P0；采样契约固定；选定单卡/单模型/单服务栈 | 计时路径可信，运行元数据齐全 |
| B | P1；P4 的最小缓存对照 | 截断信号有机制证据，合法缓存能得到正确解释 |
| C | P2；P3 的少量边界点 | 量化响应不能轻易被正常 kernel/调度变化替代 |
| D | 冻结探针；独立校准与跨会话评估；P6 | 客户端可见信号有效，规避成本和失败边界明确 |
| E | 额外硬件/引擎迁移；有需要再做 P5 | 迁移范围与额外成本有明确研究收益 |

首轮成功产物不是一个“识别 GPU”的标签，而是四份证据：响应曲线与原始记录；支持或否定机制的局部硬件 trace；同预算的误报/检出比较；无法区分的正常与偏差条件清单。

如果 P1/P2 的曲线可被合法实现轻易复现，应及时停止扩大栅格，转向条件更严格的服务契约，或把性能探针作为与 token 证据组合的辅助通道。组合后的总误报率需要重新校准。
